# 04 把经验变成可验证的原则和组件

当前 Studio 已有运行状态、活动卡片、输入栏和恢复表单。本轮把待处理摘要与活动定位接入现有组件。代码和定向测试能确认状态投影、身份匹配和跳转行为。它们不能证明用户是否更快找到下一步，仍需开发者走查。

## 从现有界面识别组件职责

| 当前组件 | 当前职责 | 待验证的问题 |
| --- | --- | --- |
| `StatusRail` 与 `statusModel.js` | 显示运行状态、连接状态和按优先级选出的待处理事项；操作入口跳到对应活动 | 用户能否在 10 秒内指出下一步？连接恢复时是否理解需要等待同步？ |
| `ChatArea` 与 `ToolCard` | 按时间呈现消息和工具活动；按结构化身份定位虚拟列表中的目标卡片 | 跳转是否把用户带到正确的调用和 Turn？键盘焦点是否可见？ |
| 工作区与技能面板 | 展示本机能力，并按来源查找技能 | 用户能否分清发现的能力和可执行的操作？ |
| 上下文视图 | 简要说明注入来源，按需展开更多信息 | 用户能否知道本轮带入了什么，而不被细节淹没？ |
| 资源管理器 | 展示运行环境的健康状况 | 用户能否把资源诊断和任务完成状态区分开？ |
| 子代理活动 | 标明更新和审批来自哪个子任务 | 用户能否看懂消息归属，并回到正确的会话处理？ |
| `UserQuestionCard` | 在对应工具活动旁显示问题和回答入口 | 问题、选项、回答状态和历史回答是否容易区分？ |
| `ApprovalDock` | 在匹配的工具活动中显示待授权动作和授权范围；找不到活动时保留在输入栏 | 用户能否看清授权对象，以及授权只作用于哪里？ |
| `TurnReconciliationForm` | 在匹配的工具活动中记录执行结果、核对依据和真实输出；找不到活动时保留在恢复提示 | 用户能否分清依据与结果，并理解保存后仍需继续原 Turn？ |
| `InputBar` 与 `PendingMessageDock` | 接收新指令、管理队列并控制当前运行 | 新消息、排队、已受理或已应用的纠偏，以及停止中或结果未确认是否容易区分？ |

组件边界先按用户要完成的动作划分，再决定是否复用视觉布局。问题回答、工具审批和结果核对可以共享标题、说明和按钮区域；它们提交的数据和影响不同，应保留各自的类型和操作。

问题回答、工具审批和结果核对现在都靠近对应的活动。Turn 检查点与 `继续当前 Turn` 仍留在 Turn 级恢复提示中。StatusRail 只摘要和定位，不承载审批或核对表单。连接未确认、会话只读或 Turn 正在停止时，相关操作会禁用。

## 候选交互原则

| 原则 | 可观察的界面要求 | 验证问题 |
| --- | --- | --- |
| 状态同时说明范围与下一步 | 显示当前 Project、Thread、Turn、状态原因和可执行动作 | 用户能否指出哪个工作在等待，以及要在哪里继续？ |
| 控件说清动作后果 | 区分回答、授权、停止、保存核对决定和继续 Turn | 点击前，用户能否说出提交后会发生什么？ |
| 控制靠近它影响的活动 | 在问题旁回答，在审批项旁授权，在待核对调用旁提交依据 | 用户能否把动作和正确的调用或 Turn 对上？ |
| 保留未确认状态 | 工具结果未知时明确显示未知，等服务端给出可操作状态 | 用户是否会把连接断开、取消接受和工具完成混为一谈？ |
| 摘要与细节分层 | 默认显示结论和下一步，把 ID、日志与技术细节放入展开区或侧栏 | 用户能否先完成任务，再按需调查细节？ |
| 多处状态保持一致 | 时间线、StatusRail 和侧栏显示相同权威状态与对象身份 | 重连后各区域是否指向同一 Project、Thread 和 Turn？ |

这些规则需要在具体场景中试用和修订。若一条规则不能改变界面决策，也无法定义可观察结果，就不应先写成长期规范。

## 当前组件边界

这些组件复用 App Server 状态，不引入第二套运行状态：

| 组件 | 输入 | 界面责任 | 当前实现 |
| --- | --- | --- | --- |
| 待处理摘要 | Project、Thread、连接、生命周期、待核对调用、审批、问题和工作流状态 | 按固定顺序显示首要事项及剩余数量；连接未同步、只读或停止时只显示等待原因。 | `statusModel.js`、`StatusRail.jsx` |
| 活动定位 | 当前待处理事项和会话消息 | 跳到对应活动并聚焦；暂时无法定位时保留原操作入口。 | `ChatArea.jsx`、`attentionTargets.js`、`ToolCard.jsx` |
| 类型化用户动作卡 | 用户问题、审批请求或工具结果核对字段 | 在对应活动中显示表单；保留各动作自己的输入、验证和提交回调。 | `UserQuestionCard.jsx`、`ApprovalDock.jsx`、`TurnReconciliationForm.jsx` |
| Turn 恢复提示 | 最近的运行状态和待核对活动 | 保留检查点和继续入口；暂时无法定位的核对操作也留在这里。 | `ChatArea.jsx` |
| 输入与队列控制 | 当前运行状态、排队消息、停止状态 | 区分新消息、待发送消息、实时纠偏和停止，并说明每种动作的后续时机。 | `InputBar`、`PendingMessageDock` |
| 上下文与能力查看 | 注入材料、已发现能力和技能目录 | 先给简短说明，再让用户展开或搜索；发现能力不代表已获授权。 | `MessageItem.jsx`、`SidePanel.jsx`、`SkillPanel.jsx`、`StatusDetailsPane.jsx` |
| 资源诊断 | Gateway 与 App Server 的进程信息 | 在设置中展示运行状况，不替代会话状态。 | `ResourceManager.jsx`、`SettingsModal.jsx` |
| 子代理会话 | 子任务进展、消息和审批 | 明确显示内容来源，避免把子代理更新误认为用户输入。 | `ChildSessionViewer.jsx`、`ChildAgentsPanel.jsx`、`App.jsx` |

这些是 UI 组合边界，不是新的运行时 API。组件接收从 App Server 状态映射出的数据，提交用户动作后调用现有控制路径；表单可以保存未提交草稿，但不能自己推断执行结果或恢复状态。

`statusModel.js` 只生成前端摘要投影。连接状态和 Turn 生命周期继续分开；审批权、工具执行结果和恢复状态仍由 App Server 确认。状态投影不新增 Gateway 或 App Server 接口。

## 用同一任务比较改动前后

请邀请 3 到 5 位开发者完成同一组任务。先在改动前版本记录基线，再在本轮实现上复测：

1. 新建会话并提交带附件的任务，展开上下文来源摘要。
2. 在工作区侧栏搜索一个项目技能，再区分环境检测结果和可执行工具。
3. 回答 Agent 提出的问题，检查工具活动并处理审批。
4. 从父会话向子会话 steer，确认子会话消息流显示来源；再检查父会话里的子代理更新和审批来源。
5. 请求停止，判断 Turn 是否已经结算。
6. 刷新或断开连接后重进会话，查看重放结果并核对工具调用。
7. 检查核对保存结果，再继续原 Turn。
8. 在设置中查看资源诊断，并在只读会话中确认哪些操作不可用。

覆盖桌面和窄屏、多个审批、停止中的审批、离屏活动、上下文来源展开、技能跨来源搜索、长时间模型请求中的 steer 与停止、父子消息来源、子会话晚打开、Gateway 退出后的恢复、断线后的结果核对和只读会话。记录用户能否说出当前状态、阻塞原因和下一步，找到正确操作的耗时、误点，以及用户如何理解上下文来源、技能来源、纠偏的受理与应用、停止的受理与结算、“保存核对”和“继续执行”。运行时记录用于确认审批、停止、核对和恢复结果。用户的判断不能替代副作用证据。

目标是至少 4/5 的参与者在 10 秒内指出下一步，找到操作的中位耗时比基线降低至少 30%，并且没有错误审批、未确认副作用重放或混淆“保存核对”和“继续执行”的情况。走查只记录任务结果和用户反馈，不记录会话内容遥测。

当前状态：代码实现和定向自动化测试已完成。3 到 5 位开发者的前后对照走查尚未执行，因此以上目标不是验证结果。基线可使用本次实现前的仓库版本，随后再用当前版本复测。

Harness 测试能证明协议和状态转换满足契约。交互走查能发现用户是否理解界面并选对动作。重构评审需要同时查看这两类证据。
