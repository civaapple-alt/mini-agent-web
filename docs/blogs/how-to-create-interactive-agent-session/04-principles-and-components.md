# 04 把经验变成可验证的原则和组件

当前 Studio 已经有运行状态、活动卡片、全局输入栏和恢复表单。这些组件展示了实际取舍，也暴露出理解成本。下列原则和组件边界是基于当前代码提出的假设，需要用户走查和运行时证据验证。

## 从现有界面识别组件职责

| 当前组件 | 已有职责 | 后续检查方向 |
| --- | --- | --- |
| `StatusRail` 与 `StatusDetailsPane` | 显示运行摘要、连接状态和详细检查点 | 摘要、原因与下一步是否层次清楚？同一 Turn 的状态是否一致？ |
| `ChatArea` 与 `ToolCard` | 按时间呈现对话和工具活动 | 用户能否快速区分模型文本、工具过程和已结算结果？ |
| `UserQuestionCard` | 在对应工具活动旁显示问题和回答入口 | 问题、选项、回答状态和历史回答是否容易区分？ |
| `ApprovalDock` | 显示待授权动作和授权范围 | 用户能否看清授权对象，以及授权只作用于哪里？ |
| `TurnReconciliationForm` | 记录未知工具调用的状态、依据和实际输出 | 依据与结果字段是否好区分？保存与继续是否组成连贯流程？ |
| `InputBar` 与 `PendingMessageDock` | 接收新指令、管理队列并控制当前运行 | 新消息、排队、纠偏和停止是否容易区分？ |

组件边界先按用户要完成的动作划分，再决定是否复用视觉布局。问题回答、工具审批和结果核对可以共享标题、说明和按钮区域；它们提交的数据和影响不同，应保留各自的类型和操作。

## 候选交互原则

| 原则 | 可观察的界面要求 | 验证问题 |
| --- | --- | --- |
| 状态同时说明范围与下一步 | 显示当前 Project、Thread、Turn、状态原因和可执行动作 | 用户能否指出哪个工作在等待，以及要在哪里继续？ |
| 控件说清动作后果 | 区分回答、授权、停止、保存核对决定和继续 Turn | 点击前，用户能否说出提交后会发生什么？ |
| 控制靠近它影响的活动 | 在问题旁回答，在审批项旁授权，在待核对调用旁提交依据 | 用户能否把动作和正确的调用或 Turn 对上？ |
| 保留未确认状态 | 工具结果未知时明确显示未知，等服务端给出可操作状态 | 用户是否会把连接断开、取消接受和工具完成混为一谈？ |
| 摘要与细节分层 | 默认显示结论和下一步，把 ID、日志与技术细节放入展开区或侧栏 | 用户能否先完成任务，再按需调查细节？ |
| 多处状态保持一致 | 时间线、StatusRail 和侧栏显示相同权威状态与对象身份 | 重连后各区域是否指向同一 Project、Thread 和 Turn？ |

这些规则需要在具体场景中试用和修订。若一条规则不能改变界面决策，也无法定义可观察结果，就不应先写成长期规范。

## 候选组件边界

后续重构可以评估以下组合。它们复用当前 App Server 投影，不引入第二套运行状态：

- **运行摘要**：整合 StatusRail 与状态侧栏入口，显示作用域、连接、生命周期、等待原因和当前可用动作。
- **活动条目框架**：统一时间线条目的标题、时间、状态和展开区，再由文本、工具、问题和恢复内容分别提供类型化主体。
- **类型化用户动作卡**：共享说明和提交反馈的视觉结构，保留问题回答、审批和结果核对各自的数据与操作。
- **Turn 恢复面板**：把未完成原因、待核对调用、核对进度和显式继续动作放在同一流程中。它只呈现 App Server 状态，不自行判断结果。
- **输入与队列控制**：把新提示、排队消息、纠偏和停止作为不同状态展示，避免用户将它们理解成同一种发送行为。

这是一组待评审的组件方向。实施前还要检查它们是否减少重复状态、缩短用户寻找下一步的路径，并且不把多个生命周期压成一个状态。

## 用可重复任务验证原则

先为当前界面建立基线，再比较一次只改一类交互的结果。每次走查都使用相同任务和初始状态：

1. 回答一个需要选项或自由文本的 Agent 问题。
2. 检查工具说明后，只批准本次操作或拒绝操作。
3. 请求停止，并判断当前 Turn 是否真的已经结算。
4. 核对一个已执行调用的依据与输出，再继续同一个 Turn。
5. 继续 Turn 后再次遇到运行中断，辨认已保存的核对决定和最新待处理调用。
6. 断开连接后重进页面，找到最新历史和有效控制。
7. 只读打开由另一个进程持有的 Session，确认哪些操作不可用。

记录任务完成率、首次选择是否正确、找到下一步所需时间、误点或重复操作，以及用户对提交后果的复述。用运行时日志核对实际状态，避免把用户主观感觉当成副作用执行证据。先测出现有界面的基线，再设改进目标；当前没有这些数据，因此本系列不声称这些原则已经被实证。

Harness 测试能证明协议和状态转换满足契约。交互走查能发现用户是否理解界面并选对动作。重构评审需要同时查看这两类证据。
