# 01 让用户看懂 Agent 当前在做什么

Web Studio 把对话、运行状态和用户控制放在同一工作区。读懂这个界面，先看每个区域回答用户的哪个问题，再看这些区域如何共同说明当前工作。

## 当前界面怎样分工

| 区域 | 当前呈现 | 用户要从这里判断什么 |
| --- | --- | --- |
| Header 与 Sidebar | Project、Thread、会话入口和连接信息 | 我正在查看哪个工作？ |
| StatusRail | 当前生命周期、连接状态、待处理事项摘要、执行设置和状态详情入口 | Agent 正在运行或等待什么？下一步要处理哪项？ |
| ChatArea | 消息、附件预览、可展开的工具详情、用户问题、历史记录和未完成 Turn 提示 | 刚才发生了什么？下一步需要处理哪条活动？ |
| 工作区侧栏 | 环境、MCP、文件与 Git、技能和工具信息 | 当前项目有哪些已发现能力？它们来自哪里？ |
| InputBar | 新消息、附件、模型选项、排队消息、纠偏和停止控制 | 我现在能做什么？输入会启动新工作、排队，还是进入当前 Turn？ |
| 运行详情与状态侧栏 | 检查点、最近进展、审批、子任务和上下文来源等详细信息 | 为什么卡在这里？注入了什么？能依据什么继续？ |

这些职责能在 [`AppLayout.jsx`](../../../frontend/src/components/AppLayout.jsx)、[`StatusRail.jsx`](../../../frontend/src/components/StatusRail.jsx)、[`ChatArea.jsx`](../../../frontend/src/components/ChatArea.jsx) 和 [`InputBar.jsx`](../../../frontend/src/components/InputBar.jsx) 中找到。`StatusDetailsPane` 展示更细的执行状态。

桌面可用宽度低于 `1100px` 时，项目侧栏折叠为图标栏；低于 `700px` 时改为可展开的抽屉。图标栏隐藏品牌名、会话列表和“最近”文字，避免内容被压成竖排；抽屉展开后恢复完整导航。

消息里的图片和粘贴文本都可以按需预览。图片预览限制在当前视口内，点图片、遮罩或收起按钮，或者按 Escape 都能返回会话；大段粘贴文本以附件入口打开，不必塞进消息气泡。工具卡片默认只显示参数摘要和状态，点击“查看详情”后才展开完整参数与输出。这样用户能主动调出所需内容，不会因鼠标经过会话流而同时出现多块浮动参数。

## 用四个问题检查一屏信息

一个状态界面至少要让用户找到四个答案：

1. 当前 Project、Thread 和 Turn 是什么？
2. Agent 正在运行、等待，还是已经结算？
3. 如果它没有继续，具体缺少什么？
4. 哪个控件会改变当前状态，点击后会发生什么？

StatusRail 提供摘要，ChatArea 保留按时间排列的活动，状态侧栏展示更详细的检查点和运行信息。这种分层能让用户按需查看细节，但也增加了跨区域理解的成本。相同 Turn 的摘要、等待原因和操作按钮需要保持一致；用户不应靠猜测在哪个面板里才能找到下一步。

StatusRail 现在按固定顺序选出一项待处理任务，并提供“前往下一项”。优先级依次是连接同步、只读或停止限制、工具结果核对、操作审批、问题回答，以及继续 Turn 或确认计划。存在多项任务时，摘要显示当前类别和剩余数量。

停止也有受理和完成两个阶段。用户发出停止请求后，Studio 会显示“停止中”；只有运行时确认本轮已经结束，提示才会清除。状态暂时不可读时，Studio 显示“结果未确认”，不会因为连接断开就猜测任务已停止。

连接恢复、只读会话和停止结算期间，StatusRail 只显示原因，不提供跳转按钮。审批、核对和问题卡也会禁用提交操作，避免用户在状态尚未确认时提交旧决定。

跳转使用 Project、Thread、Turn、`callId` 或 `interactionId` 定位活动。ChatArea 会滚动并挂载虚拟列表中的目标行，再把键盘焦点放到对应卡片。目标不在时间线时，待处理表单仍保留在原有入口。

工作区侧栏把环境能力和技能目录放在一起，但它们回答的是“运行环境发现了什么”，不是“模型获准执行什么”。环境页展示本机和项目中检测到的工具；技能页按内置、个人、项目和插件区分来源，并支持搜索。技能既可以由模型按任务选择，也可以由用户明确调用；发现一项能力本身不会扩大执行权限。

上下文也可以按需查看。会话流默认只显示注入来源的简短摘要，展开后能看到路径、技能或其他材料的来源，不展示正文。运行详情则解释模型使用量；最近请求和整个会话是不同统计范围，数据不足时会明确显示“未知”。

资源管理器位于设置中，概览 Gateway 和受管 App Server 的运行状况，帮助排查资源压力。它不代表任务已经完成或工具副作用已经发生；判断结果仍要回到会话状态。

子代理活动也要保留来源。主会话中的子代理报告会标记“子代理更新”，能识别任务时显示子任务名称；父任务运行期间收到的报告不会伪装成用户输入或直接打断父任务。子会话页面则标明哪些内容来自主会话的中途纠偏。

首字响应时间和总响应时间放在对应的用户输入下方，让一次模型请求的等待时间靠近触发它的任务。无法对应到输入时，计时信息仍留在 assistant 回复；没有可靠数据时则不显示。

这也是本系列要检视的地方。当前界面包含这些状态，并不证明信息层级已经合适。后续重构应先记录用户在哪个区域寻找状态、是否能解释下一步，再决定合并、移动或删减哪些内容。
