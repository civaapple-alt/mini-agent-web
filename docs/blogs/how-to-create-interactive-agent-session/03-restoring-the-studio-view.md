# 03 断线后怎样让界面重新对齐运行状态

连接中断时，浏览器会暂时失去新事件。界面不能据此判断 Turn 已结束，也不能把未收到的工具结果当作失败。对用户来说，恢复工作的目标是重新显示服务端当前确认的状态，并给出仍然有效的下一步。

## Studio 如何重新对齐

当前 Web Studio 先重新连接并读取会话历史，再补上断线期间错过的活动。发现事件缺口时，它会重新读取保存的会话和运行状态，而不是把本地缓存当作完整记录。

浏览器重新进入 Thread 时，Studio 还会加载最新活动、待回答问题、审批和运行状态。较早的历史按需加载。详情见 [`App.jsx`](../../../frontend/src/App.jsx) 和 [`threadHistoryPages.js`](../../../frontend/src/utils/threadHistoryPages.js)。

历史重建保留用户输入、后续纠偏和助手活动之间的原有关系，而不是把一个 Turn 压成单段回复。可用时，“已处理”耗时和模型响应时间沿用实际记录；缺少可靠数据时不显示估算值。

浏览器断线不会停止正在运行的任务。Gateway 收到 Ctrl+C 时，会停止接收新任务、请求主任务和子任务停止，再清理自己管理的进程。若退出前无法确认结果，恢复后的会话仍会如实显示未确认，不会把它改写成成功或失败。

| 用户看到的状态 | 界面当前做法 | 用户需要理解的事 |
| --- | --- | --- |
| 正在恢复连接 | StatusRail 显示连接恢复状态，历史和运行状态重新读取 | 连接恢复中，不能据此判断 Agent 已停止。 |
| 本轮未完整结束 | ChatArea 显示检查点、阶段或失败原因 | 当前 Turn 还没有完成，继续与重试可能有不同含义。 |
| 结果待核对 | 在匹配的工具活动中展示核对表单；未匹配到活动时保留在恢复提示中 | 工具结果未知，先检查真实状态。 |
| 等待继续 | 显示 `继续当前 Turn` 操作 | 核对已保存，点击后才会恢复原 Turn。 |
| 只读查看 | 禁止提交控制动作，并说明 Session 由其他进程持有 | 你可以查看状态，暂时不能控制这条运行。 |

实时事件负责及时更新界面；保存的会话历史和执行进度负责重新构建内容与状态。发现缺口时，Studio 会重新读取运行时，而不是把浏览器缓存当作完整记录。

子会话查看器可能在子任务开始后才打开。页面会把已经收到的实时活动与保存的历史合并；这能补上晚打开时错过的内容，但刷新后仍以运行时保存的历史为准。

## 哪些设计点还需要验证

当前界面把连接状态和待处理摘要放在 StatusRail，把工具核对和 Turn 级继续操作放在 ChatArea，把检查点细节放在状态侧栏。这些信息来自不同读取路径，也承担不同职责。重连时需要验证用户能否看出它们描述的是同一个 Project、Thread 和 Turn。

待核对摘要会告诉用户还有多少结果需要确认。核对表单靠近对应的工具活动，`继续当前 Turn` 留在恢复提示中。保存决定后仍需明确继续；尚未执行的操作可能会在恢复后运行。实际走查还要确认用户能否找到入口，并理解这两个动作的区别。

停止请求被接受后，界面仍显示“停止中”，直到运行时确认任务已经结束。超时或断线时，Studio 会显示“结果未确认”并允许刷新；刷新不会重新发送用户输入或工具操作。

重连后，子任务列表、子会话时间线和父会话中的报告需要重新对上。报告标记说明更新来自哪个子任务，子会话展示实际消息；暂时看不到更新不代表子代理没有运行或已经失败。

StatusRail 按对应活动定位下一步。ChatArea 会把暂时不在视图中的活动带到用户面前；若无法定位，核对入口仍留在恢复提示中。断线、只读和停止结算期间，Studio 不提供过期操作。

任务结束或核对决定提交后，Studio 会重新确认运行状态。若核对请求失败，页面会检查是否已保存；如果保存成功但状态暂时读不到，也会把两件事分开说明。

恢复路径不应自动重发用户输入或重跑结果未知的工具。Studio 应明确显示 `状态尚未确认`，并保留能解释下一步的上下文。若连接本身也未恢复，则应显示读取失败或等待状态，不能填入猜测的完成结果。
